What it is

A question-answering system that reads a private library of PDFs and answers in its own words, with every sentence tied to the page it came from. It runs entirely on one laptop, with the network off.

You type a question. The system finds the pages that discuss it, gives those passages to a small language model, and the model answers in at most four sentences with a letter after each factual sentence. Clicking the letter opens the original PDF at that page. If the library does not contain the answer, the expected reply is NOT FOUND rather than a guess.

The one-sentence version. It is a search engine over your own PDFs whose answers you can check in one click, built to run on a machine with 4 GB of video memory and no internet connection.

Why it exists

Three constraints shaped every design choice. Everything below follows from them, which is also why some "obvious" upgrades are missing on purpose.

  1. The documents cannot leave the machine. They are official reports and academic papers, some not public. A hosted API would mean uploading them and trusting a third party with copies; that was ruled out first, not last.
  2. The answers have to be checkable. A fluent paragraph is worthless in this domain if the reader cannot find the sentence it came from. Citations therefore point at a page, and the evaluation scores pages, not vibes.
  3. The hardware is a laptop. An RTX 3050 with 4 GB of VRAM and 16 GB of RAM. That is enough for a 4-billion-parameter model and nothing larger, so the design deliberately spends the GPU on the generator and runs parsing and embeddings on the CPU.

The scale it is built for

The design target is a corpus of about 100,000 pages. This manual describes a working system at 851 pages, with the per-page costs measured so the large corpus is a matter of time rather than a redesign: the index would be about 0.96 GB and a full parse about 32.5 hours at the measured rate.

How it works, stage by stage

Six stages. Each one states what it does and what was actually measured on this corpus.

1

Parse

PDF pages become line-preserving text blocks, table regions and page numbers. Scanned pages are OCR'd only where there is no text layer, and the page number is always the physical PDF page, because that is what a citation opens.

851 pages, 242 table regions, 86 OCR pages in 996.1 s (51.3 pages/min); 5,511 / 5,520 numeric tokens match the page's own words.

2

Chunk

Text is split by heading, never across one, so every chunk carries its section path. Each detected table becomes one chunk with its caption, units and notes; table text is removed from the prose chunks so the same numbers cannot be retrieved twice.

3,226 chunks (2,958 text + 268 table); 37 table chunks carry a printed caption, 52 carry units.

3

Index

Two indexes over the same chunks: BM25 over the words (exact strings, numbers, names) and a dense vector table in LanceDB, built with bge on the CPU so the GPU stays free for the model.

LanceDB table is 8.03 MB for this corpus; 9,602 bytes per page, so 0.96 GB at 100k pages.

4

Retrieve

A question is answered from the best-matching pages. The current ranking is page-level BM25, which beat a three-list hybrid on the measured questions; the hybrid is kept as evidence in retrieval/.

recall@5 25/26, MRR 0.885 (page BM25) against 24/26 and MRR 0.832 (hybrid).

5

Answer

Up to four passages are labelled A-D and sent with strict rules: use only these passages, put the passage letter after every factual sentence, and reply NOT FOUND when the answer is absent.

23/30 on the oracle test; about 3.7 s and 13.5 tokens/s for a real question in the UI.

6

Cite

The letters become buttons that open the cited PDF at the cited page, served from data/corpus/ over localhost. A reader checks the claim against the page itself, not against a quote the model wrote.

Each answer lists its sources as label + page, e.g. A Marahatta 1970 p2.

What it cannot do, and where it stops

A manual that lists only strengths is a sales page. These are the known limits, each one a deliberate trade rather than an oversight.

  • The corpus is 97 documents, not 100,000. Every 100k-page figure in this manual is an extrapolation from measured per-page costs (32.5 h to parse, 0.96 GB of index), not a run. Nobody has parsed 100k pages.
  • Two PDFs yield no text at all. They are kept and reported rather than replaced: a truncated file and a page with no extractable layer. Their absence is visible in the corpus report.
  • The evaluation set is 30 questions, 26 answerable. That is small. It is enough to catch a regression the size of seven questions and not enough to claim a two-point improvement; the release gate is per question, not an average.
  • Publisher is known for about half the documents. The folder gives it for reports; papers print a journal name on page 1 for only a few. 58 documents have no outlet on their first page, so the field stays empty instead of borrowing the topic folder name.
  • Table captions are found for 37 of 268 table chunks. 210 detected tables carry no printed caption within 160 points of the table, which is a property of the corpus, not a parser bug. Every table chunk says whether it has a caption rather than inventing one.
  • Step 5 (hybrid retrieval) is measured but not finished. The ablation table, the held-out run and the offline proof for that step are still open; the deliverable so far is the measurement and the decision to keep the simpler retriever.

Run it yourself

On the machine that holds the corpus and the models. Everything is local; the first two commands need the pinned models already on disk.

# 1. parse the PDFs (851 pages take ~17 minutes; resumable)
.venv\Scripts\python.exe -m ingest.cli build

# 2. build the chunks, then the dense index (CPU; ~5 minutes for 3,226 chunks)
.venv\Scripts\python.exe -m chunk.cli build
.venv\Scripts\python.exe -m chunk.dense

# 3. start the model and the UI, then open http://127.0.0.1:8000
.\scripts\launch-llm.ps1
.venv\Scripts\python.exe -m uvicorn ui.server:app --host 127.0.0.1 --port 8000

# 4. check the system's own health line (model, UI, index)
.\scripts\health.ps1

# 5. score retrieval on the eval set
.venv\Scripts\python.exe eval\run_retrieval.py --label my-run

Expected from step 4 on a healthy machine: READY model=qwen3.5:4b loaded ui=127.0.0.1:8000 ok index=97 docs/851 pages.

Glossary

TermPlain meaning
RAGRetrieval-augmented generation: find passages first, then let the model answer only from them.
ChunkA passage the system searches: a section of prose, or one table with its caption, units and notes.
BM25A classic keyword-ranking formula. Strong when the question quotes exact words, numbers or names.
EmbeddingA vector of numbers representing a passage's meaning, so paraphrases can be found without sharing a word.
RRFReciprocal rank fusion: combine two ranked lists by their positions rather than by scores, which are not comparable.
Oracle testGive the model the correct page and ask the question anyway. It measures the answer step without retrieval noise.
Recall@kShare of questions whose correct page appears in the top k results.
MRRMean reciprocal rank: 1.0 means the correct page is always first.
