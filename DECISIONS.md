# Decisions

Format: ID, date, decision, reason, alternatives rejected. Never delete entries; supersede them.

## Decided
- **D-001 (2026-11-13) Fully offline, local only.** Cloud APIs rejected.
- **D-002 Generator is a 3-4B model at Q4 on GPU.** Reason: 4GB VRAM. 7B+ spills to RAM and is too slow. Final pick by benchmark in Step 2.
- **D-003 Hybrid retrieval (dense + BM25, RRF) in LanceDB.** Reason: exact lookups matter; embedded, no server. Rejected: Qdrant/Weaviate (server), Chroma (weaker hybrid).
- **D-004 CPU reranker on top 30-50.** Tuned on eval.
- **D-005 Two-tier PDF parsing.** PyMuPDF4LLM for all pages, Docling or pdfplumber only for table pages. Reason: 100k pages, tables matter. Rejected: heavy parsers on all pages (too slow, GPU contention).
- **D-006 Eval first (Step 1), before building.** Accuracy must be measured from the start.
- **D-007 Retrieval metrics and answer metrics tracked separately.**
- **D-008 Regression gate (rewritten by D-022).** No retrieval or prompt change is accepted if the eval score drops. Local-LLM-judge faithfulness is a secondary signal only, never a gate.
- **D-009 Per-document LLM context (2 lines), not per chunk.** Reason: cost on 100k pages.
- **D-010 Citations verified in code; "not found" decided by reranker-score gate.**
- **D-011 Docs-only phase.** No code or installs until docs and each step are approved.
- **D-012 Rejected:** GraphRAG/Neo4j, agentic loops, per-chunk LLM context, generator fine-tuning. Experiments backlog (HyDE, multi-query, RAPTOR-style, embedder/reranker fine-tuning) only if eval shows a specific failure, behind a flag.

## Suggested by Claude during review, approved by the owner (2026-11-13). Owner may reverse any of them.
- **D-022 Regression gate rewritten (refines D-008 and D-016).** Reason: the old text said one question is about 3 points, but the gate runs on the 20 dev questions where one question is 5 points, and not-found accuracy is scored on about 3 questions (one flip = 33 points). "No metric may drop" would block good changes on noise. New rule: no unexplained pass-to-fail question, and no drop of more than one question on any metric. Also: every later failure becomes a new dev question (owner-approved), growing dev toward about 50-60 by Step 5; held-out stays frozen at 10; re-baseline whenever the dev set changes. See `EVAL.md`.

The LibreOffice version is pinned; changing it needs owner approval and a re-check of every gold page. Reason: a converter change would silently shift pages and break the gold sources.
- **D-024 Version control and rollback.** The owner runs `git init` and makes the first commit before Step 0 (D-032); commit after each verified sub-task with the step number in the message; tag `step-NN-approved`; never rewrite history (use `git revert`). Reason: several free agents, and one bad session must not destroy working code.
- **D-025 Protected files, owner-only edits (suggested by Claude, approved by owner):** `AGENTS.md`, `PLAN.md`, `REQUIREMENTS.md`, the metric definitions and gate in `EVAL.md`, existing eval questions and splits, existing `DECISIONS.md` entries, and the text of step tasks and definitions of done (agents may only tick a verified checkbox). Agents write proposals in `STATUS.md`. Pre-commit check of `git diff --name-only`; an optional pre-commit hook that blocks protected-file edits is proposed in Step 0 for owner approval. `REQUIREMENTS.md` and the step files are protected too, because an agent could otherwise weaken its own definition of done.
- **D-026 Offline is enforced, not just stated.** Offline environment variables set in launch scripts, local model folders, a list of every downloaded file, and an offline proof run with the network disabled at the end of Steps 0, 5, 6 and 8 (Step 7 already requires it). Not yet verified for our exact library versions.
- **D-027 Step 8 re-checks the not-found questions** against the full corpus, and the runbook (Step 9) repeats the check whenever documents are added. A not-found question that becomes answerable is replaced with owner approval, never silently.

## Suggested by Claude during second review, approved by the owner (2026-11-13). Owner may reverse any of them.
- **D-028 Approvals cannot be forged (suggested by Claude, approved by owner; refines D-024, D-025).** Only the owner creates `step-NN-approved` tags and writes approvals. Approvals live in a new owner-only file, `APPROVALS.md`, written only in `OWNER:` commits; the "Approved by owner" and "Date" columns are removed from the `STATUS.md` tracker. *Design note:* the first idea was an owner-only approval column in `STATUS.md`; a separate protected file is simpler for small agents to follow (they cannot tell which cells of a shared file are owner-only) and is checked the same way as every protected file. Before a completion approval the owner runs the tamper checks in `APPROVALS.md` (see D-033). Agents run as the same OS user, so this detects tampering rather than blocking it; the optional pre-commit hook (Step 0) adds a block.
- **D-029 Gate drift closed (refines D-022).** Each change is compared with the last accepted baseline and with the baseline from the start of the step, with a total drop of at most one question per metric (MRR: 1/N). Not-found accuracy (a) must not drop at all. Reason: five changes that each pass with a one-question loss would otherwise lose five questions; on about 3 not-found dev questions one question is a third of the unanswerable ones. Cost: a change that helps false "not found" (b) but costs one (a) is blocked unless the owner changes the rule.
- **D-030 Corpus layout (refines D-023).** `data/corpus/` is the only folder the system reads and mirrors the folders of `data/raw/`. Native PDFs are NTFS hardlinks to `data/raw/` (no extra disk; fallback is copying if the Step 0 test fails, with a disk-budget re-check). Word files become `<original name>.pdf` (for example `report.docx.pdf`), which avoids a clash with a native `report.pdf`. SHA-256 is recorded for every corpus file, so an in-place change to a hardlinked original is caught.
- **D-031 Owner edits and the clean-tree rule (refines D-025).** The owner commits their own edits first with an `OWNER:` message. Agents run `git status` at session start and stop if a protected file has uncommitted changes (or the tree is not clean), without committing, stashing or resetting. Agents stage files by name (never `git add -A`) and check the staged list for protected files, so an owner's uncommitted edit cannot be swept into an agent commit or deadlock the agents.

- **PROPOSED D-049 Parser choice per page type, and why the table grid is filled from words.** Measured on the real corpus (2026-11-14):

  | Page type | Pages | Parser | Evidence |

  | Text, no table | 31 | `pymupdf4llm` (no OCR) | 73.1 pages/min without table detection |
  | Table detected by PyMuPDF | 7 | PyMuPDF cell grid + the page's own word list | fixes `69.85` → `6985\n.`, `2.51` → `251\n.`, `14.07` → `1407\n.`; **393/393 numeric tokens now match the page's words** |

- **PROPOSED D-064 Parsed output is stored as per-document shards keyed by SHA-256, and the corpus-wide artifacts are assembled from them in corpus order (Step 8, needs owner approval).** Each document's parse writes `index/parsed/shards/<sha256>.{search.json,structure.jsonl,summary.json}`; `assemble` walks `corpus.files()` order and writes `index/pages.json` and `index/parsed/pages.jsonl`. - **PROPOSED D-065 Duplicate documents are flagged exact by SHA-256 or near by at least 80% shared page-text hashes, and are never deleted or indexed (Step 8, needs owner approval).** A row becomes `duplicate` with `duplicate_of` set; `status` lists it and the report counts it. Reason: a second copy under another name would otherwise compete with the original in retrieval and split citations between two identical documents, while deleting a file the owner placed in the corpus would break provenance and the read-only rule. 80% (of the smaller document's pages) was chosen so a re-exported or re-saved copy is caught without flagging two papers that share an introduction; the case suite covers exact, near and distinct documents (`ingest/test_pipeline.py`).

- **PROPOSED D-076 Parse isolation uses a subprocess child, not `multiprocessing` spawn (Step 12 implementation finding, needs owner approval).** D-075 proposed a short-lived child per document and the step text named `multiprocessing.get_context("spawn")`.
